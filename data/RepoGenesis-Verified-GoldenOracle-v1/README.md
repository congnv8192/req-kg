# RepoGenesis (Verified) — Golden Oracle Implementations

Reference implementations for the 30 repositories in the **RepoGenesis (Verified)** subset,
shared for non-commercial academic research.

- Paper: *RepoGenesis: Benchmarking End-to-End Microservice Generation from Readme to Repository* (ACL 2026)
- Public benchmark: <https://github.com/microsoft/DKI_LLM/tree/main/RepoGenesis>

Please read `TERMS_OF_USE.md` before using this archive, and `NOTICE.md` for third-party
attributions.

## What a golden oracle is

Quoting the paper (Appendix, *Golden Oracle Implementation*):

> The reference implementation used for validation and as the basis for test generation.
> For real-world repositories, this is the original GitHub codebase. For expert-supervised
> repositories, this is the implementation generated by Gemini 3 Pro under expert supervision.

Two consequences are worth keeping in mind if you plan to treat these as ground truth:

1. The expert-supervised oracles are **model-generated under human supervision**, not
   human-authored. They are a validated reference, in that the released test suite passes
   against them, but they are not the only correct implementation of the requirement.
2. The oracle is **not** part of the evaluation path. Evaluated systems receive only the
   README, and scoring is black-box against the test suite. So an oracle records one way to
   satisfy the requirement, not the definition of a correct answer.

## Coverage

All 30 Verified repositories are accounted for: 25 ship as source, 5 as pinned upstream
commits.

| Group | Count | Delivery |
| --- | --- | --- |
| Expert-supervised, Python | 16 | source |
| Expert-supervised, Java | 8 | source |
| Real-world, `django-rest-framework-crud` | 1 | source |
| Real-world, remaining | 5 | pinned upstream commit |

The five pinned repositories (`flask`, `eve`, `synapse`, `SimpleFastPyAPI`,
`rock-paper-scissors-flask`) are third-party open source under their own licences, some of
which do not permit redistribution under the benchmark's own terms. Pinning them by commit
is both licence-clean and more precise than a copy, since it reproduces the exact tree used
in the paper:

```bash
cd real_world && ./fetch_oracles.sh
```

The script writes to `real_world/checkouts/` by default; pass a path to change that. It needs
`git` and network access.

## Test suites

Every `tests/` directory (Python) and `src/test/` directory (Java) in this archive is copied
verbatim from the public benchmark release, **not** from our internal oracle working copies.
Those working copies had drifted from the published suites, so this guarantees that what you
analyse here matches what you downloaded from GitHub.

## Reproducing an oracle

The Python oracles are ordinary applications with a `requirements.txt`. The published tests
are black-box HTTP tests that expect a server on port 8080, so a typical loop is:

```bash
cd expert_supervised/python/TaskManagement
python -m venv .venv && .venv/bin/pip install -r requirements.txt -r tests/requirements.txt
.venv/bin/uvicorn main:app --host :: --port 8080 &
.venv/bin/python -m pytest tests -q
```

Binding to `::` rather than `127.0.0.1` matters on hosts where `localhost` resolves to IPv6
first, which the test suites assume.

The Java oracles are Maven projects; `mvn test` from the repository root is enough. Build
output (`target/`) has been stripped.
